The main lesson of this assignment was that the three cafés needed three different scraping strategies, even though they all serve HTML. Lakeshore Lattes was a pure CSS selector problem. I used class selectors to find each card, and the sibling selector (~) to connect a section heading to the cards that follow it. Hilltop Grind was easier: an id selector (#menu) plus pd.read_html turned each table into a DataFrame, and melt reshaped the wide S/M/L columns into one row per item and size. Canal Street was the hardest because nothing is in the HTML until JavaScript runs. A headless browser had to select a shop from the dropdown, click Show full menu, and then keep clicking Show more. Each item’s prices then lived on a separate page, so I had to crawl by reading each link’s href attribute and visiting it.

My first Canal Street scraper returned too few rows because I read the page before the JavaScript finished loading. Replacing a fixed sleep with waiting for a specific element to appear fixed it. The same lesson applies to pagination: I looped on Show more until the button disappeared, rather than guessing how many clicks to make. For Lakeshore, inner_text returned the price line with the NEW! badge and dietary tags mixed in. Cleaning that text in clean_card_lines and parse_price_line before building a DataFrame was easier to test than fixing it afterward in pandas.

Matching taught me why a human in the loop matters. Normalization (lowercasing, stripping accents and filler words, sorting word order) handled 28 of the 46 rival items automatically, but no single threshold handled the rest correctly. “Matcha Latte” scores 87 against “Mocha Latte” but is a different drink, while “PSL” scores 18 against “Pumpkin Spice Latte” but is the same drink. A high threshold misses real matches, and a low one creates false ones. Splitting scores into bands (auto-accept, ask a person, auto-reject) and saving each answer with record_decision meant the owner only answers what the code can’t decide, once. The screenshots show how costly errors are: two wrong review answers moved the result from 25 below / 10 above the market to 13 above the market.

For the analysis, pivot_table made the comparison simple: one row per item and size, one column per café, with row-wise .mean(axis=1) for the rivals’ average. The gap analysis was an outer merge with indicator=True. The _merge column labels each row left_only, right_only or both, which gives “only we sell” and “only the rivals sell” directly. Returning constants like BELOW_ALL instead of emoji strings avoided typos.

If I did this again, I would start Canal Street with playwright codegen instead of writing clicks from scratch. I would write the cleaning tests first, since they run in under a second. I would add a check that the row count is 144 so a silently short scrape gets noticed, and I would log each match decision’s score so the owner can see why the code asked. For next month’s rerun, the biggest risk is that a café changes its HTML and a selector silently returns nothing, so the scraper should fail loudly when a count looks wrong. Overall the assignment took me about nine hours, and Canal Street and match_items took the longest.
